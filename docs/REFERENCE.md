### Undocumented subcommands (verified to exist)

These are how notebooks get authored programmatically. They are not in `--help`.

```
ntopcl convert    <input.json> <output.ntop>  --dev-blocks-on=True
ntopcl exportjson <input.ntop> <output.json>  --ext --dev-blocks-on=True
```

- `convert` reads a notebook-recipe JSON and writes a real `.ntop` file.
- `exportjson` is the inverse and round-trips (verified on a real 360-block notebook with three
  notebook inputs, which produced 3.7 MB of JSON).
- Caveat seen on export: `[W]: Cannot include list<point> as leaf in recipe` - literal
  `list<point>` leaves are dropped on `exportjson`. Build `list<point>` from
  `core.list<point>` wrapping `point<real,real,real>` blocks instead of literal leaves.

## 4. The block universe

`ntopgen` reads `vendor/functions.json` (853 blocks in the version used here), `vendor/types.json`
and `vendor/type_defaults.json`. **These files are not in this repository.** They are nTop's block
and type API surface, they are specific to one nTop version, and some entries are not publicly
released. `scripts/bootstrap.py` locates them on your own machine; see the README.

A function entry looks like:

```json
{
  "description": "Return the absolute value of a Scalar number.",
  "displayname": "Abs",
  "function": "abs<real>",
  "inputs": [{"cardinality":"one","description":"Value to operate on.","name":"Operand",
              "parameterization":0,"type":{"type":"real"},"unitsMult":[1,1]}],
  "output": {"type": "real"},
  "releasestage": 2, ...
}
```

- `function` is the exact block ID used in the recipe JSON. Overloads are distinguished by the
  angle-bracket signature; revisions by a trailing `[maj.min.patch]`.
- An input `type` may carry `"dep": <index>` meaning "same type as input N" (e.g. `core.if`).
- An input may carry `"unitsReq"` as an int meaning "same required units as input N".
- `output` may carry `"dep": <index>` meaning the return type follows input N.

## 5. The recipe JSON schema

Top-level keys of a notebook recipe (from a real round-tripped notebook):

```json
{
  "body": [ <block>, ... ],     // root blocks, ordered; index == position
  "inputs": [ <input>, ... ],   // notebook inputs, ordered; index == the "input" reference number
  "cbRefs": [], "imports": [],
  "description": "", "displayname": "",
  "name": "user_func_<32 random chars split 8_4_4_4_12>",
  "namespaces": [],
  "version": [1, 0, 0]
}
```

### A function block

```json
{"func": "sphere<point,real>", "id": "inst117", "name": "Sphere_0",
 "type": "implicit", "inputs": [ <arg>, <arg> ]}
```

- `id` must be unique and of the form `inst<N>`. `notebook_author` starts N at 101.
- `type` is the block's resolved return type.
- `name` is optional; nTop autogenerates one if absent.
- `inputs` is positionally aligned with the function's `inputs` array in `functions.json`.
  `null` means "unfilled".

### A variable block (a named, referenceable value in the notebook root)

```json
{"id": "inst276", "name": "Panel Break Span %", "type": "real",
 "variable": true, "contents": <block or literal or null>}
```

### Referring to another root block or variable, from an input slot

```json
{"props": [], "ref": {"id": "inst276"}}
```

### Referring to a notebook input, from an input slot

```json
{"input": 0, "props": []}
```
`0` is the index into the top-level `inputs` array.

### A notebook input declaration

```json
{"name": "Span", "description": "", "type": "real",
 "dimension": {"length": 1},
 "contents": {"type":"real","value":{"isFinite":true,"units":{"length":1},"val":3.048}}}
```
`contents` is the default value. `dimension` is the physical dimension.

### Literal values, by type

All lengths are in **metres**. All angles in **radians**. `units` is a dimension map.

```json
{"type":"real",             "value":{"isFinite":true,"units":{"length":1},"val":0.01}}
{"type":"real",             "value":{"isFinite":true,"units":{},"val":0.001}}
{"type":"integer",          "value":{"val":3}}
{"type":"bool",             "value":{"val":true}}
{"type":"text",             "value":{"string":"A-CAD.step"}}
{"type":"file_path",        "value":{"val":"C:/path/with/forward/slashes/name"}}
{"type":"point",            "value":[{"isFinite":true,"val":0.0},{"isFinite":true,"val":0.0},{"isFinite":true,"val":0.0}]}
{"type":"real_field",       "value":{"expression":"(3*x + 2*y - z)/1mm","units":{}}}
{"type":"unit_length_enum", "value":{"id":"mm"}}
{"type":"<anything>_enum",  "value":{"enum":0}}
```

Note the two enum encodings seen in the wild: `{"id":"mm"}` for `unit_length_enum` and
`{"enum":0}` for generic enums. Prefer `{"enum":N}` unless a real notebook shows otherwise for
that specific enum, and verify by round-tripping.

A `list<T>` is NOT a literal - it is a block:
```json
{"id":"inst120","func":"core.list<point>","type":"list<point>","inputs":[<point>,<point>,...]}
```

## 6. Validation loop for any notebook we author

1. Emit recipe JSON.
2. `ntopcl convert recipe.json out.ntop --dev-blocks-on=True` - must exit 0.
3. `ntopcl -t out.ntop` - writes input/output JSON templates. Confirms the input schema we
   intended is what nTop sees.
4. `ntopcl -j input.json -o output.json out.ntop -v 2` - runs it.
5. CORRECTED 2026-08-17 by WP1, empirically. **Exit code 72 is NOT a success code.** The
   `run-ntop-automate` skill claims it is; that is wrong for these builds. A notebook with a
   negative sphere radius returned 72 and wrote no output JSON at all. Observed codes:
   `convert` success 0, `convert` failure 1, `-t` success 0, run success 0 (both 5.53.2 and
   5.54.0), run with a block error 72, missing `inputs` in the input JSON 1, `exportjson` 0.
   Gate success on the expected artefacts existing and being non-empty, and always surface the
   real return code.
6. Optional: `ntopcl exportjson out.ntop roundtrip.json --ext --dev-blocks-on=True` and diff
   against the input recipe to catch anything nTop silently rewrote.

## 7. nTopCore (available, probably not needed)

`<your nTop Core distribution>` - a Windows DLL + C header exposing implicit-body queries
(field eval, gradient, closest point, slicing, meshing by dual contouring, transform, scale).
It CONSUMES `.implicit` files exported from nTop; it cannot author geometry.
Python examples at `nTopCore/examples/python/`. Only reach for this if we need field queries
outside nTop, e.g. to sample the outer mould line for the aero model.

## 8. Things that do NOT work - do not retry

- `pip install suave` - wrong package.
- Authoring `.ntop` by editing the binary. It is a custom container (`MAGIC%$1` header, named
  chunks `turhe`, `sf2`, `sf2_metadata`, `sf2_state`, `sf2inp0`...). Use `ntopcl convert`.
- `ntopcl convert <in.ntop> <out.json>` - wrong direction, errors with
  `Notebook argument must have ".ntop" file extension.` Use `exportjson`.
- numpy >= 2 or scipy >= 1.14 with SUAVE.
- setuptools >= 81 with SUAVE.
